# ui-ux-pro-max

Проектный стандарт визуального дизайна и UX для SEIVA. Применять при любой работе над `apps/web/app/**`. Для общей анти-AI-slop механики (композиция, микровзаимодействия, готовые компоненты) используй глобальный скилл `hallmark` как инструментарий — этот файл фиксирует, как он преломляется именно для SEIVA: какая эстетика, какие токены, какие экраны и их специфичные состояния.

## Контекст продукта

SEIVA — инструмент менеджера MICE-агентства для сборки клиентской презентации поездки. Два разных пользователя интерфейса:
1. **Менеджер** работает в форме/редакторе — инструмент должен быть быстрым, плотным, без лишнего трения.
2. **Конечный клиент** видит только итоговую презентацию/PDF — это должно выглядеть как продукт премиального ивент-агентства, не как внутренняя админка.

Отсюда — рабочие экраны (`/`, `/drafts`, `/programme/[id]`) и презентационный экран (будущий, этап 5 плана) визуально родственны, но не идентичны: у презентации выше планка полиграфического качества.

## Текущее состояние (диагноз, чтобы не откатиться)

`globals.css` — нетронутый Next.js стартер (Arial/Helvetica, дефолтные `--background`/`--foreground`). Экраны собраны на сырых Tailwind-утилитах без системы: `bg-amber-50`/`amber-200`/`amber-500` вперемешку с `zinc-900` и точечным `emerald` для статусов — случайный, а не спроектированный набор. Это ровно тот дефолтный «Tailwind-стартер» вид, который нужно осознанно заменить фирменной палитрой, а не продолжать растаскивать по случайным оттенкам.

## Обязательные правила

1. **Осознанная палитра, не дефолтная.** Выбери 1 акцентный цвет + 1 нейтральную шкалу + отдельные семантические цвета для saving/saved/error — и заведи их как CSS-переменные в `globals.css` (`@theme inline`), а не разбрасывай `amber-500`/`emerald-600` по компонентам. Любой новый экран берёт цвет из токенов, а не выдумывает свой оттенок.
2. **Типографика — иерархия, не единый размер.** Максимум 3–4 ступени размера на экран (заголовок экрана / заголовок секции / тело / вспомогательный текст). Сейчас `text-3xl`/`text-2xl`/`text-xl`/`text-sm`/`text-xs` используются вперемешку без системы — свести к шкале и использовать её последовательно.
3. **Состояния — часть дизайна, не заплатка.** Для каждого экрана с данными: пустое состояние, загрузка, ошибка, успех должны быть спроектированы заранее, с тем же визуальным языком, что и «счастливый путь» (пример, который уже сделан правильно — пустое состояние `/drafts`; довести остальные экраны до этого уровня).
4. **Плотность соответствует роли экрана.** Форма брифа и редактор программы — рабочие инструменты менеджера: плотнее, меньше воздуха, быстрее сканируются глазами. Презентационный экран (когда дойдём до этапа 5) — противоположный полюс: много воздуха, крупная типографика, минимум UI-хрома (кнопок/рамок), как в настоящей презентации.
5. **Автосохранение и async-статусы должны быть однозначно читаемы.** Статус в редакторе программы (`saving`/`saved`/`error`) — не терять при рефакторинге: пользователь должен всегда понимать, сохранены ли его правки, без гадания.
6. **Доступность — минимум по умолчанию.** Видимый `:focus` на всех интерактивных элементах (сейчас не задан явно — полагается на дефолт браузера, это хрупко при кастомных цветах фона). Контраст текста к фону ≥ WCAG AA. У всех `<input>`/`<select>`/`<textarea>` — связанный `<label>` (это уже соблюдается — не регрессировать).
7. **Порядок и перестановка — с явной affordance.** Кнопки «Вверх/Вниз/✕» для дней и блоков в редакторе — минимально жизнеспособный вариант; при следующей итерации рассмотреть drag handle с явной иконкой, а не голый текст кнопки.
8. **Не плодить одноразовые классы-снежинки.** Если один и тот же набор Tailwind-классов (карточка, инпут, кнопка-primary, кнопка-secondary) повторяется 3+ раза — вынести в общий компонент (`packages/ui` по плану, либо локальный `components/` в `apps/web` на текущем этапе), а не копировать строку класса по файлам.

## Процесс для любой задачи на UI

1. Определи роль экрана (рабочий инструмент менеджера vs презентация для клиента) — это задаёт плотность и тон, до выбора цвета единой кнопки.
2. Сверься с токенами палитры/типографики (или заведи их, если это первая задача, где их ещё нет).
3. Спроектируй все состояния экрана (empty/loading/error/success), не только «счастливый путь».
4. Проверь фокус-стили и контраст перед тем как считать задачу готовой.
5. Если создаёшь визуально новый паттерн (не форму/карточку/кнопку, а что-то untried) — прогони через `hallmark` на анти-AI-slop, прежде чем фиксировать как стандарт.
