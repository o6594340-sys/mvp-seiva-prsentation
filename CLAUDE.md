# SEIVA MVP — контекст проекта

> Этот файл — источник истины по проекту вместо повторного чтения `brief.md` и `plan.md` в начале каждой сессии.
> Правило поддержки: в конце сессии, где были значимые изменения (новая фича, смена решения, смена стека, готовый этап), обновляй раздел «10. Текущий статус реализации» и, если изменился сам план — соответствующие разделы выше. Не жди явной просьбы — это часть обычной работы.

## 1. Что это за проект
Веб-инструмент для менеджера MICE-агентства (корпоративные поездки, инсентивы, конференции):
заполнить бриф → получить программу по дням от AI → отредактировать → собрать презентацию → экспортировать в PDF.

Полные первоисточники (уже учтены здесь, перечитывать не нужно): `brief.md`, `brief.docx`, `plan.md`.

## 2. Зафиксированный scope MVP

### Обязательно в первом релизе
1. Форма брифа с обязательной валидацией.
2. Поддержка нескольких стран + опция «предложить альтернативу».
3. Генерация программы по дням в структурированном формате.
4. Редактор программы: правка текста, перестановка блоков и дней.
5. Замена каждой картинки вручную.
6. Автосохранение в черновик.
7. Формирование презентации из утвержденного документа.
8. Экспорт в PDF.

### Вне MVP (сознательно не делаем)
- импорт PDF/DOCX/XLSX;
- роли и личные кабинеты;
- многопользовательская совместная работа;
- поставщики, цены, интеграции DMC;
- PPTX-экспорт и сложные шаблоны;
- авто-переписывание контента после каждого ручного изменения.

## 3. Обязательные поля брифа
1. Количество участников.
2. Сфера компании.
3. Тип мероприятия: инсентив, конференция, VIP, круглый стол и др.
4. Страны (множественный выбор + добавление вручную).
5. Галочка «предложить альтернативу стране».
6. Примерный возраст участников.
7. Соотношение мужчин и женщин (формат «70/30»).
8. Интерес к спорту/экстриму.
9. Цель поездки.
10. Ограничения/что нельзя.
11. Количество дней поездки (обязательно — точную дату не все знают, а число дней знают всегда).
12. Дата заезда (необязательно; если задана — дни в программе подписываются календарными датами, если нет — просто «День 1», «День 2» и т.д.).
13. Интенсивность программы: Умеренная / Активная / Насыщенная (с утра до вечера) — добавлено по фидбэку 2026-08-10 взамен использования поля «интерес к спорту/экстриму» для темпа программы; это два разных измерения (спорт/экстрим — про тип активностей, интенсивность — про плотность расписания).

## 4. Пользовательский поток
1. Менеджер заполняет бриф.
2. Система генерирует предварительную программу по дням.
3. Менеджер правит программу и содержание блоков.
4. Система формирует финальный текст презентационного уровня.
5. Менеджер меняет изображения при необходимости.
6. Формируется презентация.
7. Результат сохраняется в черновик и экспортируется в PDF.

## 5. Целевая техническая схема (по плану)

**API (целевой, из плана):**
- `POST /api/briefs` — сохранить бриф.
- `POST /api/programmes/generate` — сгенерировать программу через AI.
- `PATCH /api/programmes/{id}` — обновить программу после ручной правки.
- `POST /api/programmes/{id}/presentation` — собрать презентацию.
- `POST /api/programmes/{id}/export-pdf` — экспорт PDF.
- `POST /api/assets/upload` — загрузка и замена изображений.

**Данные (минимум, из плана):** briefs, programmes, programme_days, programme_blocks, presentations, drafts, assets.

**AI-слой (правила):**
1. Ключ AI только на сервере.
2. На вход AI — только структурированный бриф.
3. Ответ принимается только в JSON по схеме.
4. При невалидном JSON — один автоповтор.
5. Если повтор неудачен — честная ошибка, без фейкового контента.

**Рекомендованный стек по плану:** Next.js (App Router) + TypeScript + Tailwind, API Routes, PostgreSQL + Prisma, S3-совместимое хранилище файлов, Zod-валидация, Playwright/Puppeteer для PDF, GigaChat как первый AI-провайдер.

**Целевая структура (по плану, ещё не создана):** `apps/web`, `packages/ui`, `packages/core`, `packages/ai`, `packages/db`.

## 6. Фактический стек (что реально стоит сейчас)
- Next.js 16.3.0 (App Router), React 19.2.8, TypeScript, Tailwind CSS 4.
- Хранилище данных: **плоские JSON-файлы** `apps/web/data/briefs.json` и `apps/web/data/programmes.json` — PostgreSQL/Prisma ещё не подключены.
- Валидация: ручная (написана вручную в route-хендлерах), Zod не подключен.
- AI-провайдер для `POST /api/programmes/generate`: **OpenAI (gpt-4o по умолчанию, `apps/web/lib/openai.ts`)**. Есть также рабочий клиент GigaChat (`apps/web/lib/gigachat.ts`), но роут сейчас использует OpenAI — см. §10 почему. `POST /api/briefs` по-прежнему генерирует через стаб отдельно (не вызывает AI) — стаб и настоящая AI-генерация это два разных пути, оба ведут в одну и ту же схему программы.
- Ключи в `apps/web/.env.local` (в `.gitignore`, не в репозитории): `GIGACHAT_AUTH_KEY`/`GIGACHAT_SCOPE`, `OPENAI_API_KEY`/`OPENAI_MODEL`.
- Монорепо-разделение на `packages/*` пока не сделано — весь код в `apps/web`.

## 8. Реализовано сейчас
- Форма брифа (`app/page.tsx`) со всеми полями из раздела 3, включая количество дней (обязательно), дату заезда (опционально) и интенсивность программы; клиентская валидация обязательных полей, добавление/удаление стран, форматирование соотношения м/ж как `NN/NN`. После сохранения — сразу редирект в `/programme/{id}` (не промежуточная панель с кнопкой: та жила только в React state и терялась при обновлении страницы — реальный баг, пойманный пользователем при первом собственном тесте формы 2026-08-11).
- `POST /api/briefs` — валидирует payload, сохраняет бриф в `data/briefs.json`, тут же генерирует программу через `buildStubProgramme()` (детерминированный стаб, генерирует ровно `durationDays` дней: день заезда → N ключевых дней → день отъезда, либо один комбинированный день при duration=1; интенсивность меняет плотность блоков — «Насыщенная» добавляет доп. блок в день, «Умеренная» добавляет упоминание свободного времени; никакого сырого текста вида «темп задан как X» в вывод не попадает) и сохраняет в `data/programmes.json` вместе со `startDate`, скопированным из брифа.
- `GET /api/briefs` — список брифов (используется страницей `/drafts`).
- **Схема программы поддерживает концепт-документ** (2026-08-10, под скилл `mice-copywriter`): `SavedProgramme.conceptSummary` (суть концепции, 1 предложение), `SavedProgramme.voice` (регистр — свободная строка, в UI подсказка из 4 регистров скилла), `ProgrammeDay.rhythm` (строка ритма дня), `ProgrammeDay.highlight` (фраза-соль дня). У стаб-сгенерированных программ эти поля всегда `null` — заполняются вручную в редакторе (или в будущем AI-генерацией).
- Редактор программы (`app/programme/[id]/page.tsx`): правка названия концепции, сути концепции, регистра (select с 4 вариантами), даты заезда, названий/ритма/highlight каждого дня, полей блока (время/заголовок/описание), перестановка дней и блоков вверх/вниз, добавление/удаление дня и блока, автосохранение с debounce 800мс через `PATCH /api/programmes/{id}`, индикатор статуса сохранения. Календарная дата каждого дня не хранится отдельно — вычисляется на лету из `startDate` программы и позиции дня (`dayNumber`), поэтому при перестановке дней даты остаются привязаны к позиции, а не к содержимому.
- Кнопка **«Сгенерировать через AI»** в шапке редактора — вызывает `POST /api/programmes/generate` для брифа текущей программы (с подтверждением, т.к. полностью перезаписывает текст), обновляет форму результатом. Проверено вживую через Playwright (клик → диалог подтверждения → генерация → новый текст на экране, без ошибок в консоли).
- **Загрузка/замена/удаление картинки на каждый блок** (2026-08-11): `POST /api/assets/upload` принимает multipart-файл (JPEG/PNG/WebP/GIF, до 8 МБ), сохраняет в `apps/web/public/uploads/<uuid>.<ext>` (папка в `.gitignore` — реальные фото клиентов не попадают в репозиторий), возвращает `{ url }`. В редакторе на каждом блоке — превью (или заглушка «Нет фото»), кнопка «Добавить/Заменить фото», «Удалить фото». `ProgrammeBlock.imageUrl: string | null` — заполняется только вручную, AI его не генерирует.
- `/drafts` — список черновиков с ключевыми полями брифа (включая длительность/даты/интенсивность) и ссылкой на программу.
- Три реальных черновика на `/drafts`: Япония «TOKYO: NEXT VERSION» и Грузия/Армения «ВЫДЕРЖКА» (текст написан вручную по `mice-copywriter`), и Япония «JAPAN / TECHNOLOGY AND TRADITION» (текст сгенерирован через `POST /api/programmes/generate` реальным вызовом OpenAI — живое доказательство, что AI-пайплайн работает end-to-end).
- **`POST /api/programmes/generate`** (`apps/web/app/api/programmes/generate/route.ts`): принимает `{ briefId }`, строит системный промпт из `mice-copywriter/SKILL.md` + `references/tokyo-system-reboot.md` (с явным запретом копировать референс дословно), пользовательский промпт — бриф + требование точного числа дней + явная проверка соответствия `restrictions`; вызывает AI-провайдера, парсит JSON (с учётом markdown-обрамления), валидирует форму и точное число дней, при неудаче — один автоповтор с более жёсткой инструкцией, при повторной неудаче — честная ошибка 502 (см. §5 «AI-слой», правила 3–5 соблюдены). При успехе перезаписывает программу и возвращает её.

## 9. Не реализовано (относительно плана)
- PostgreSQL + Prisma — сейчас JSON-файлы вместо БД (а изображения — на локальном диске в `public/uploads`, не в S3-совместимом хранилище, как указано в целевом стеке).
- Zod-схемы для брифа и AI-ответа.
- Сборка презентации (`POST /api/programmes/{id}/presentation`) и экран предпросмотра.
- Экспорт в PDF (`POST /api/programmes/{id}/export-pdf`).
- Разделение на `packages/ui`, `packages/core`, `packages/ai`, `packages/db`.
- В схеме концепт-документа пока нет полей под опциональные секции скилла (highlights-recap по всей поездке, раздел про еду/детали, заметка про визуальный язык презентации) — сделаны только основные: `conceptSummary`, `voice`, `days[].rhythm`, `days[].highlight`.

## 10.5. Проектные скиллы
- `.claude/skills/mice-copywriter/SKILL.md` (+ `references/tokyo-system-reboot.md`) — копирайтинг текста презентации уровня «продающий», не шаблонный стаб: governing concept на всю поездку, названные реальные места/форматы (не абстракции), день-режим с rhythm/highlight-строками, **4 регистра голоса** (Возвышенный/Дерзкий/Вдохновляющий/Спокойный нейтральный — выбираются под аудиторию вместе с подбором активностей, не по отдельности), запрет калек с английского и запрет «мы»-панибратства с гостем (см. правила 10–11, обращение «Вы»/«вы» по регистру). Референс — реальный пример текста, присланный пользователем, с разбором почему он работает.
- `.claude/skills/ui-ux-pro-max.md` — стандарт визуального дизайна экранов SEIVA: палитра-токены вместо дефолтных Tailwind-цветов, иерархия типографики, спроектированные состояния (empty/loading/error/success), разная плотность для рабочих экранов менеджера и презентационного экрана клиента.

## 10. Текущий статус реализации (обновляется по ходу работы)
**Дата последнего обновления: 2026-08-11.**

Готово: Этап 1 (каркас) и Этап 2 (бриф) из плана — частично (данные в JSON, не в БД). Этап 3 (генерация) — есть оба пути: быстрый стаб в `POST /api/briefs` (шаблонный текст) и настоящая AI-генерация в `POST /api/programmes/generate` через `mice-copywriter` (см. ниже про выбор провайдера). Этап 4 (редактор) — готов, включая загрузку/замену/удаление изображений на блок, дату заезда, календарные даты по дням и весь концепт-документ. Этапы 5 (презентация/PDF) и 6 (QA) — не начаты.

**Баг, пойманный при живом тесте загрузки картинок (2026-08-11):** после добавления `imageUrl` в схему блока валидация PATCH требовала поле строго `null`/строка — но черновики, созданные ДО этого изменения, хранили блоки вообще без поля `imageUrl` (не `null`, а полностью отсутствует). Итог: попытка сохранить любую правку в старом черновике возвращала 400 и автосохранение молча не срабатывало. Исправлено — валидация в `api/programmes/[id]/route.ts` теперь принимает `undefined` наравне с `null`. **Урок на будущее: при добавлении нового поля в существующую схему — валидация обязана быть терпима к данным, созданным до этого поля, а не только к новым.**

Репозиторий на GitHub: https://github.com/o6594340-sys/mvp-seiva-prsentation (ветка `master`, `data/` и `.env.local` в `.gitignore` — реальные брифы клиентов и ключи AI туда не попадают).

**AI-провайдер: сравнили GigaChat и OpenAI на одном и том же брифе (Япония, IT, ограничение «конференция во второй день»), два прогона каждый:**
- **GigaChat** — дважды поставил конференцию не в тот день (нарушил `restrictions` даже после явной команды в промпте перепроверить это построчно), и почти дословно скопировал `references/tokyo-system-reboot.md` вместо своей концепции при первой попытке.
- **OpenAI (gpt-4o)** — с первой попытки: ограничение соблюдено точно, концепция и набор локаций полностью свои (не пересекаются с референсом), 1-2 лёгких клише поправить руками, но в целом уровень черновика для правки менеджером, а не заготовки с нуля.
- **Решение:** роут `POST /api/programmes/generate` сейчас использует `lib/openai.ts`. Клиент GigaChat (`lib/gigachat.ts`) оставлен в коде нетронутым — можно вернуться/переключиться одной строкой импорта, если появится причина (например, цена в масштабе).
- Стоимость по факту пренебрежимо мала: один прогон промпта (~10к токенов на вход, весь скилл+референс) — единицы центов на gpt-4o.

Пользователь смотрел черновик 2026-08-10 и запросил ряд правок, все внедрены в этой сессии:
1. В бриф добавлены «количество дней» (обязательное) и «дата заезда» (опциональное) — программа генерируется на нужное число дней, дни подписываются датами, если дата задана.
2. Добавлено отдельное поле «интенсивность программы» (Умеренная/Активная/Насыщенная) — раньше плотность расписания ошибочно завязывалась на поле «интерес к спорту/экстриму» и выводилась в тексте буквально («темп задан как…»); теперь это два разных поля.
3. Прислан референс продающего текста (Tokyo/System Reboot) — на его основе создан и несколько раз доработан скилл `mice-copywriter`: сначала под конкретный бриф, затем добавлены 4 регистра голоса под разную аудиторию (фарма 60+ ≠ IT-инсентив), затем — запрет калек с английского и запрет «мы»-панибратства («заселяемся», «ужинаем» → безличная форма или обращение на «вы»/«Вы»).
4. Схема `ProgrammeDay`/`SavedProgramme` расширена под концепт-документ (`conceptSummary`, `voice`, `days[].rhythm`, `days[].highlight`), редактор дополнен соответствующими полями.
5. Подключена настоящая AI-генерация (`POST /api/programmes/generate`), опробована на GigaChat и OpenAI, выбран OpenAI по итогам честного сравнения (см. выше).
6. Кнопка «Сгенерировать через AI» подключена в редактор (было — только прямой вызов API); заодно исправлен реальный баг, найденный пользователем: после сохранения брифа кнопка перехода в редактор жила только в React state и терялась при обновлении страницы — теперь сразу редирект.
7. Загрузка/замена/удаление изображений на блок — последний обязательный пункт MVP-скоупа (§2.1) закрыт.

**Следующий разумный шаг (нерешено, требует выбора пользователя):**
- (а) Сборка презентации из утверждённого документа + экран предпросмотра (§2.1 п.7) — следующий недостающий пункт MVP по порядку.
- (б) Экспорт в PDF (§2.1 п.8) — тоже недостающий пункт MVP, естественно идёт после презентации.
