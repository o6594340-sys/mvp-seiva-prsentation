## 1. Цель
Создать русскоязычный веб-инструмент для MICE-агентств. Менеджер заполняет короткую форму по запросу клиента, получает от AI содержательную предварительную программу поездки, редактирует её и превращает в аккуратную презентацию/PDF.
Главный результат MVP — не красивая обложка, а программа, которую менеджер может показать клиенту как предварительное предложение.
## 2. Граница MVP
В первом релизе поддерживается один надёжный сценарий:
`Форма брифа → AI-программа → редактор программы → выбор визуального стиля → веб-презентация/PDF`.
Не начинать разработку с импорта PDF/DOCX/XLSX, личных кабинетов, многопользовательского доступа, поиска изображений, поставщиков, цен, PPTX или интеграций с DMC. Всё это последующие этапы.
## 3. Пользователь
Менеджер российского MICE-агентства. Ему нужно за несколько минут отправить клиенту осмысленное предварительное предложение без подтверждённых цен, чтобы:
- сузить направление или согласовать программу;
- показать, чем будут заняты участники;
- собрать комментарии клиента;
- передать выбранный сценарий на дальнейший расчёт.
## 4. Обязательная форма брифа
Все поля на русском. Если критичное поле не заполнено, генерация не запускается.
| Поле | Тип | Правило |
| --- | --- | --- |
| Режим работы | Переключатель | «Есть направление» / «Нужно предложить направления» / «Есть готовая программа» |
| Направление | Текст или список | Обязательно для режима «Есть направление»; можно указать до 3 вариантов |
| Город вылета | Текст | По умолчанию «Москва», менеджер может изменить |
| Период | Текст + при возможности даты | Принимает «октябрь 2026», «12–16 октября», ошибки формата не блокируют работу |
| Количество участников | Число | Обязательное |
| Продолжительность | Число дней/ночей | Обязательное |
| Тип компании / отрасль | Текст | Например: IT, автомобильная, фарма, гостиничная |
| Кто едет | Текст | Возраст, роль, темперамент, уровень активности |
| Цель | Текст | Тимбилдинг, конференция, поощрительная поездка, стратегия и 
т.п.
 |
| Что обязательно | Теги + текст | Например: море, гастрономия, командная активность, деловая сессия |
| Что нельзя / ограничения | Текст | Например: спокойный темп, без сложных переходов, без визовых рисков |
| Дополнительный комментарий | Большое поле | Свободный текст менеджера |
Для режима «Есть готовая программа» менеджер вставляет программу вручную в большое поле. На MVP не требуется чтение Word/PDF.
## 5. Правила выбора направления
1. Если менеджер указал одно направление, AI работает только с ним. Нельзя предложить другой город или страну без отдельной отметки «разрешить альтернативы».
2. Если менеджер указал 2–3 направления, AI создаёт отдельную концепцию/программу для каждого указанного направления. Не добавляет посторонние страны.
3. Если направление открыто, AI сначала отдаёт максимум 3 карточки выбора направления, а не полноценные туры: почему подходит, сезон, логистика/въезд как «требует проверки», риск или ограничение.
4. После выбора одной карточки AI создаёт программу только по выбранному направлению.
5. Европа не должна автоматически исключаться или запрещаться. Если её выбрал менеджер, система обязана показать заметку о пересадках, визе и необходимости актуальной проверки.

### 6.2. Качество программы
Каждый день должен отвечать на вопрос клиента: «Что именно мы будем делать?»
Требования:
- 3–5 осмысленных блоков на день;
- конкретные форматы, районы, объекты или виды активности, если они уместны;
- не использовать пустые фразы вроде «культурный формат», «маршрут по городу», «мягкое прибытие», «перезагрузка команды» без расшифровки;
- не повторять одинаковые экскурсии каждый день;
- учитывать возраст, отрасль, цель, размер группы и темп;
- писать естественным литературным русским языком, без кальки с английского и лишних длинных тире;
- не придумывать подтверждённые рестораны, отели, рейсы, цены, доступность или визовые правила;
- все факты, которые могут меняться, маркировать: «предварительно, требует подтверждения».
### 6.3. Концепция
AI предлагает две концепции на выбор. Каждая проходит через название, описание дней, 
highlights
, гастрономию и, при уместности, идеи подарков.
Пример принципа: для молодой IT-компании в Японии концепция может связывать инновации, ритм города и командное взаимодействие. Это не повод писать абстрактные лозунги вместо программы.
## 7. AI-архитектура
1. Ключ AI хранится только на сервере в переменных окружения. Никогда не передавать ключ в браузер или репозиторий.
2. Клиент отправляет форму на `POST /
api
/
programmes
/
generate
`.
3. Сервер передаёт модели только структурированный бриф и системный 
master
 
prompt
 MICE-редактора.
4. Сервер валидирует JSON по схеме. Если JSON 
невалиден
 — один повторный запрос на исправление формата.
5. Если AI не ответил или ответ всё ещё 
невалиден
, показать честную ошибку и кнопку «Повторить». Нельзя показывать шаблонный тур вместо результата.
6. В ответе сохранять технические поля: `
generationId
`, `
provider
`, `
model
`, `
createdAt
`, `
promptVersion
`. Их показывать только в режиме разработки/администратора.
7. Для готовой программы использовать отдельный режим AI-редактуры: сохранять факты и обязательные элементы, но разрешать улучшать заголовки, объяснения, группировку и подачу. Не подменять программу каталогом.
## 8. Master 
prompt
: ключевые правила
System 
prompt
 должен включать:
- роль: 
senior
 MICE-копирайтер и продюсер программ;
- русский язык: литературный, живой, точный, без англицизмов и штампов;
- обязательное использование всех существенных фактов брифа;
- запрет на выдуманные подтверждённые факты;
- обязательную конкретику в каждом дне;
- требование возвращать только JSON по схеме;
- запрет на шаблонные фразы и повторяющиеся блоки;
- правило: если направление задано, не менять его;
- правило: при недостатке фактов сформировать разумное предварительное допущение и явно пометить его.
Пользовательский 
master
 
prompt
, подготовленный заказчиком, подключается в серверный вызов как отдельный 
versioned
-файл, а не копируется в UI-компоненты.
## 9. Редактор программы
После ответа AI открывается один понятный документ, а не набор ячеек и служебных кнопок.
Менеджер может:
- редактировать любой заголовок и текст прямо в документе;
- удалить, добавить, дублировать и переставить день/слайд;
- добавить отдельный слайд про отель, ужин, площадку или активность;
- заменить изображение на своё;
- сохранить изменения автоматически в черновик.
Редактор не обязан на MVP автоматически переписывать текст после каждого ручного изменения. Достаточно хорошей адаптивной вёрстки с ограничением длины и подсказкой «текст слишком длинный для слайда».
## 10. Презентация
Презентация строится только из утверждённого документа. Она не имеет права повторно генерировать программу, менять страну или заменять текст статическим каталогом.
Базовая последовательность слайдов:
1. Обложка: название, направление, период, группа, логотип агентства.
2. Идея поездки: выбранная концепция.
3. Почему направление подходит сейчас: только если есть проверенные/помеченные предварительные данные.
4. Маршрут одним взглядом.
5. По одному насыщенному слайду на каждый день.
6. 
Highlights
.
7. Гастрономия.
8. Отель — только если он задан.
9. Практические замечания и дисклеймер.
На каждом слайде одна мысль. Текст должен быть крупным и читаемым при экспорте в PDF. День: максимум 3–5 коротких блоков, а не мелкая таблица.
## 11. Визуал MVP
- Только русский интерфейс и русский результат.
- Три фиксированных профессиональных стиля с безопасными палитрами.
- Пользователь выбирает стиль и одну из четырёх заранее подготовленных палитр; свободный выбор любых цветов не нужен.
- У агентства можно загрузить только свой логотип.
- Изображение в каждом слайде — слот: стандартное референсное фото, загрузка собственного файла или замена позже.
- Если фото нет, использовать нейтральную фирменную заглушку, а не картинку другого направления.
- Режим менеджера и режим клиента должны быть разными: в клиентском нет кнопок, предупреждений и служебных полей.
## 12. PDF
- Сначала рабочая веб-презентация, затем экспорт PDF.
- Формат 16:9.
- Экспорт не зависит от ширины окна браузера.
- Основной текст на логическом полотне 1440×810: не меньше 16 
px
; заголовки больше.
- Если текст не помещается, создаётся продолжение, а не уменьшается шрифт до нечитаемого размера.
- PPTX не входит в MVP.
## 13. Что нельзя делать
- Нельзя подменять результат AI заранее написанным маршрутом.
- Нельзя использовать один и тот же тур для разных брифов.
- Нельзя автоматически менять заданное направление.
- Нельзя экспортировать пустой каркас как готовую программу.
- Нельзя писать «подтверждено», если это не проверено поставщиком.
- Нельзя делать PDF до проверки содержимого в редакторе.
- Нельзя смешивать импорт, исследование, генерацию, визуал и PDF в одном первом релизе.
## 14. Критерии приёмки MVP
MVP считается готовым, если для трёх тестовых брифов — например, молодая IT-компания в Дубае, автомобильная компания в Китае и спокойная группа 50+ в Грузии — выполняются все пункты:
1. У каждого брифа программа соответствует только указанному направлению.
2. В каждом дне есть конкретное содержание, а не общие формулировки.
3. Программа учитывает аудиторию и задачу.
4. В презентации видны дни, 
highlights
 и концепция именно этого ответа AI.
5. Ни один экран не показывает демо-тур как результат ошибки.
6. Менеджер меняет текст, копирует/добавляет/переставляет слайд и загружает своё изображение.
7. PDF читается на ноутбуке без увеличения.
8. При ошибке AI пользователь видит ошибку и повтор, а не чужую программу.
## 15. Порядок разработки
1. Форма брифа и серверный вызов AI.
2. Валидация JSON + три реальных тестовых брифа.
3. Редактор программы.
4. Презентация из редактора.
5. PDF.
6. Стили, палитры, изображения.
7. Импорт DOCX/PDF/XLSX.
8. Пользователи, агентства, изоляция данных, опубликованные ссылки и платежи.
Нельзя начинать следующий пункт, пока предыдущий не проверен на трёх реальных брифах.
